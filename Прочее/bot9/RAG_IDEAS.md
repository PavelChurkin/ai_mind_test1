# Как улучшить RAG

Это предложения для следующих версий, а не включённые по умолчанию изменения. Сейчас `rag.py` читает книги и рефлексию, режет текст на фрагменты, индексирует слова с лемматизацией; необязательный векторный поиск дополняет поиск по словам. `/раг вкл` сначала отвечает по найденным фрагментам, затем при отсутствии ответа переходит к обычному ответу с явной пометкой. Разовый `/раг вопрос` остаётся строгим поиском по книгам.

`rag2.py` (`/раг2`) уже реализует первое улучшение: иерархический пересказ. Векторы считаются от пересказов фрагментов, поиск объединяет их с поиском по словам в оригинале, а модель получает исходные фрагменты. Остальное ниже относится к обеим базам.

## Сначала измерять качество

Собрать небольшой набор вопросов по настоящим книгам: точные цитаты, перефразирования, разные падежи, уточнения «а почему он так считал?», несколько источников, вопросы без ответа. Для каждого вручную отметить правильные фрагменты, ожидаемые источники и допустимость отказа. Отделить набор для подбора настроек от контрольного набора.

Измерять долю найденных правильных фрагментов в первых k результатах, корректность цитат и ссылок, долю уверенных ответов без доказательств, лишних отказов, время и стоимость ответа. Хранить версию книг, настройки индекса и результаты рядом: иначе изменение модели или чанкинга нельзя честно сравнить. Отдельно проверять свежезаписанную и заменённую рефлексию: удалённый текст не должен возвращаться из индекса или кэша.

## Сравнить /раг2 с /раг

Положить одни и те же книги в `RAG` и `RAG2`, прогнать размеченный набор через оба индекса и сравнить долю правильных фрагментов отдельно для перефразирований и для точных цитат. Сравнивать честно: у `/раг` без `RAG_EMBEDDINGS` поиска по смыслу нет, поэтому добавить третий вариант — эмбеддинги исходных фрагментов. Пересказы стоят денег и времени, поэтому смысл оставить их есть, только если они заметно лучше.

По тому же набору подобрать `RAG2_DENSE_MIN_SIM`: при слишком низком пороге вопрос не по книгам получит случайные фрагменты вместо честного «не нашлось», при слишком высоком перефразирования не найдутся. Сравнить `RAG2_CHUNK_CHARS` и модели эмбеддингов; оценить, сколько пересказов теряют имена и не добавляет ли модель фактов, которых нет во фрагменте. Измерить настоящую стоимость сборки на одной книге, прежде чем индексировать библиотеку.

Возможные продолжения: дополнительно отдавать соседние фрагменты, пересказы глав как второй уровень иерархии, получать вектор по нескольким переформулировкам пересказа.

## Разбивать по смысловым границам

Сначала выделять книгу, главу, раздел, абзацы и страницы, затем собирать фрагменты в пределах токенного бюджета модели. Короткий фрагмент удобен для поиска, но отрывает довод от предпосылок: при передаче модели можно добавить соседние абзацы того же раздела. Сохранять устойчивый идентификатор, заголовок, страницу и диапазон текста, чтобы ссылка открывала проверяемое место.

Сравнить нынешние фрагменты примерно по 1000 символов (в `/раг2` — по 2000) с несколькими размерами и перекрытиями на контрольных вопросах. Для PDF отдельно оценивать качество извлечения и распознавания: скан без текстового слоя требует OCR, а колонтитулы и переносы слов лучше очищать до индексации. Ошибку чтения показывать владельцу, а не превращать в «книга проиндексирована».

## Объединять поиск по словам и смыслу

Для имён, терминов и цитат полезен точный поиск с лемматизацией; для перефразирований — многоязычные эмбеддинги, проверенные на русском философском тексте. Объединять списки результатов, например по рангам, вместо прямого сложения несопоставимых оценок разных методов. Затем выбирать разнообразные фрагменты, убирая почти одинаковые соседние куски одной книги.

Эмбеддинги считать при изменении файла, хранить модель и её версию в индексе. Смена модели требует переиндексации. Небольшая локальная модель или отдельный поисковый сервис могут снизить нагрузку основного процесса; выбор делать по измерениям памяти и задержки. Не включать тяжёлый `sentence-transformers` без оценки ресурсов сервера.

## Переранжировать небольшой список

Сначала быстро получить, например, 20–40 кандидатов, затем более точной моделью оценить соответствие вопросу и оставить несколько лучших. Подбирать число кандидатов, конечный k и порог отказа по тестовому набору. Дорогой переранжировщик запускать только при неоднозначных результатах; логировать, какие фрагменты он исключил и почему выбранный путь дал ответ или отказ.

## Понимать уточнения в диалоге

Прежде чем искать по «а что он говорил про это?», строить самостоятельный поисковый вопрос из нового обращения и небольшого релевантного контекста. Учитывать выбранный интервал и внимание, но не превращать всю переписку в поисковую строку. Сохранять исходный вопрос для ответа, ограничивать число поисковых переформулировок и проверять, что они не добавляют утверждений пользователя от себя.

Закреплённое внимание — контекст беседы, а рефлексия — отдельный редактируемый источник. Указывать их происхождение и не выдавать пользовательскую мысль за цитату из книги. При общих книгах и отдельных коллекциях бесед фильтровать доступ до поиска и переранжирования.

## Проверять доказательства ответа

Требовать ссылки на номера фрагментов для каждого содержательного утверждения; проверять существование ссылок программно, цитаты — по исходному тексту. Отдельным коротким шагом проверять, подтверждают ли фрагменты ответ, и при недостатке доказательств делать явный отказ. Самооценка LLM не заменяет проверку на размеченных примерах.

Тексты книг, пересылки и рефлексию передавать как данные с обозначенным происхождением: инструкция «игнорируй предыдущие правила» внутри книги не должна менять правила бота. Добавить такие случаи в тесты. Сохранять явное различие между ответом по источникам и обычным ответом после неудачного поиска.

## Управлять бюджетом и наблюдать результат

Считать токены всей заявки: роль, история или интервал, внимание, найденные фрагменты, вопрос и запас на ответ. Бюджет истории в символах не гарантирует, что всё вместится в окно модели. При нехватке места предлагать пользователю явно сузить интервал; не обрезать незаметно требуемые «все сообщения». Для обычной истории можно использовать уже имеющееся сжатие, а для RAG — меньше более релевантных фрагментов.

В отладочный лог писать длительность чтения, поиска, переранжирования и генерации, число кандидатов/фрагментов/токенов, версию индекса и причину перехода к обычному ответу. Полные тексты оставлять только в явно включённом режиме отладки. Кэшировать поиск по ключу из вопроса, доступа, версии индекса и настроек; при изменении книг или рефлексии инвалидировать кэш.

## Порядок внедрения

1. Размеченный набор вопросов, метрики, журналы и точные ссылки на источники.
2. Разбиение по разделам и соседний контекст; сравнение с нынешним индексом.
3. Гибридный поиск и удаление дублей; затем ограниченное переранжирование.
4. Переформулирование вопросов с учётом диалога и проверка доказательств.
5. Кэш и оптимизация ресурсов только после измерения качества и стоимости.

Каждое изменение проверять на одном и том же контрольном наборе. Сначала улучшать поиск подтверждающих фрагментов: более длинный промпт и большее число чанков сами по себе не гарантируют правильный ответ.

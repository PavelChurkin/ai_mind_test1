## Почему запросы уходят, а бот пишет «Не получилось сформулировать ответ.» / «Мысль не родилась»

**Главная причина — модель-«рассуждалка» тратит весь лимит токенов на рассуждение.** `deepseek-v4-flash` перед ответом «думает»; токены рассуждения входят в `max_tokens` и оплачиваются, но в текст ответа не попадают. Стандартный лимит `MAX_TOKENS_DEFAULT` — 800 токенов. Если вопрос заставил модель думать дольше, она упирается в лимит, API возвращает пустой `content` с `finish_reason="length"` — запрос ушёл, деньги списаны, а bot5 видел просто пустую строку и писал «Не получилось сформулировать ответ.» (для `/мысль` — «Мысль не родилась»: там три запроса подряд, хватит одного пустого). Ещё хуже при маленьком лимите: `/лимит токенов 30 000` bot5 понимал как 30 токенов (см. [ниже](#лимит-токенов-сбрасывается-быстрее-чем-за-час)), и тогда пустыми выходили почти все ответы.

Остальные причины того же сообщения: ошибка API (нет денег, 400/429/5xx, таймаут) и пустой ответ с `finish_reason="stop"` (бывает у модели, ничего не поделать).

Что сделано в bot6:

- **Повтор с большим лимитом.** Пустой ответ из-за лимита — один повтор с `EMPTY_ANSWER_RETRY_TOKENS` (3000) токенов. Если лимит и так не меньше — повтора нет.
- **Причина видна.** Если ответа всё равно нет, бот пишет служебным сообщением (с «⚙️», в контекст модели не попадает и в дневной лимит не считается), почему: «Не получилось сформулировать ответ. Причина: модель израсходовала весь лимит на рассуждение даже при 3000 токенах. Можно поднять лимит: «/лимит токенов 4000» (админ) или задать в настройках LLM_EXTRA_BODY, отключающий рассуждение.» Для ошибки API — текст ошибки.
- **Строка в логе на каждый запрос** (и в обычном режиме): время, `finish_reason`, токены входа и выхода, сколько из них ушло на рассуждение, лимит, длина ответа:
  ```
  LLM: 4.2 с, finish=length, токены: вход 3120, выход 800, из них рассуждение 800 (лимит 800), ответ 0 символов
  WARNING пустой ответ: модель израсходовала весь лимит (800 токенов) на рассуждение и не успела написать ответ — повтор с лимитом 3000
  ```
- **`LLM_EXTRA_BODY`** — дополнительные параметры запроса, например `{"thinking": {"type": "disabled"}}`, если провайдер позволяет выключить рассуждение. По умолчанию `None`: какие параметры принимает ProxyAPI для этой модели, на живом API не проверено.

## Картинки: CERTIFICATE_VERIFY_FAILED, а потом 400 «Received 429 … fetching image from URL»

Это одна цепочка из двух ошибок.

1. **Сертификат.** Фото ВК лежат на `*.userapi.com`; их сертификат подписан корневым центром **HARICA TLS RSA Root CA 2021**. Его нет в старых хранилищах сертификатов (на Windows он догружается только через Windows Update, на сервере — в старом пакете `ca-certificates`), отсюда `unable to get local issuer certificate`. В пакете `certifi` он есть — это проверено тестом `test_real_contexts_include_certifi_with_harica_root`.
2. **Ссылка вместо картинки.** Не скачав картинку, bot5 передавал модели ссылку (`— передаю ссылкой`). Тогда картинку качает уже сервер ProxyAPI, а серверы ВК отвечают ему **429 Too Many Requests** (запросы с чужих серверов ВК ограничивает). ProxyAPI превращает это в `400 Bad Request: Received 429 status code when fetching image from URL` — и весь ответ пропадает.

В bot6:

- скачивание идёт по цепочке: системные сертификаты → `certifi` → свой файл `IMAGE_CA_FILE` (если задан) → без проверки (только если `IMAGE_SSL_INSECURE_FALLBACK = True`, по умолчанию выключено);
- не скачанная картинка **пропускается** (строка в логе `— картинка пропущена`), а не отправляется ссылкой; вернуть старое поведение — `IMAGE_URL_FALLBACK = True`;
- если API всё же отверг запрос с картинками — один повтор без них, как в bot5, но без повторного скачивания;
- последние `IMAGE_CACHE_SIZE` (16) картинок хранятся в памяти: одна и та же картинка из истории не качается на каждый ответ.

Если ошибка сертификата осталась и с `certifi` — значит, трафик идёт через прокси или антивирус, подменяющий сертификаты: укажите его корневой сертификат в `IMAGE_CA_FILE`.

## Режим подробного лога

```bash
python bot6.py                        # обычный режим: запуск, ответы, строка на запрос к LLM, ошибки
python bot6.py --debug                # подробно; то же — переменная окружения BOT_DEBUG=1
python bot6.py --log-file logs/bot6.log   # ещё и в файл (ротация при LOG_MAX_MB = 50 МБ)
```

В обычном режиме из лога убраны строки `HTTP Request: POST …` от библиотек (они были на каждый запрос). В режиме `--debug` для основных функций (обработка сообщения, пачка обращений, сборка истории, запрос к LLM, картинки, команды, РАГ, пересказ) пишется вход с аргументами, выход с результатом и время, а для запросов к LLM — промпт целиком и ответ модели. В строке лога видно имя функции:

```
2026-10-20 12:00:01,204 DEBUG gran wrapper: >> answer_batch(2000000001, [Request(…)])
2026-10-20 12:00:05,410 DEBUG gran _llm_request: LLM system: …
2026-10-20 12:00:05,412 DEBUG gran wrapper: << answer_batch = None за 4.21 с
```

## Серверный запуск: перезапуск раз в неделю с очисткой логов

```bash
python bot6_server.py                     # перезапуск раз в 7 суток, лог — logs/bot6.log
python bot6_server.py --restart-days 3    # раз в 3 суток (0 — не перезапускать)
python bot6_server.py --debug             # бот с подробным логом
```

[`bot6_server.py`](bot6_server.py) запускает `bot6.py` отдельным процессом и следит за ним:

- бот, проработав срок (`--restart-after-hours`, сервер передаёт его сам), **дожидается, когда никто не ждёт ответа** (нет обращений в очереди, недописанных команд и паузы), и выходит с кодом 75. Сервер стирает лог и его ротации и запускает бота заново — файл лога не растёт;
- бот упал — перезапуск через 5 с, 10 с, 20 с… до 5 мин (проработал 10 мин без падений — снова с 5 с). Лог при этом **не стирается**: в нём причина падения;
- бот завис и не вышел через час после срока — сервер останавливает его и запускает заново, лог сохраняется;
- «Грань, стоп машина» (бот выходит с кодом 0) — сервер тоже завершается; Ctrl+C или SIGTERM — сервер передаёт сигнал боту, ждёт и выходит.

Даже без сервера лог в файл не растёт бесконечно: `--log-file` ротируется при `LOG_MAX_MB` (50 МБ), хранится `LOG_BACKUPS` (1) старый файл.

**Linux, systemd** (`/etc/systemd/system/gran.service`, потом `systemctl enable --now gran`):

```ini
[Unit]
Description=Бот «Грань» (bot6)
After=network-online.target

[Service]
WorkingDirectory=/opt/gran/Прочее/bot6
ExecStart=/usr/bin/python3 bot6_server.py
Restart=on-failure
User=gran

[Install]
WantedBy=multi-user.target
```

**Windows:** `python bot6_server.py` в консоли или задача в «Планировщике заданий» с триггером «При запуске компьютера».

## Длинное обращение или /роль на несколько сообщений

**Да, теперь бот это понимает** (в bot5 — нет: он отвечал на первую часть, а остальные считал обычными сообщениями беседы; `/роль` обрезалась на первой части). ВК режет сообщение длиннее 4096 символов на несколько. bot6 считает сообщение продолжением, если предыдущее сообщение того же автора длиннее `SPLIT_MIN_PART_CHARS` (3000 символов) и следующее пришло не позже `SPLIT_JOIN_SEC` (10 с) по дате ВК:

- **обращение к боту** — части склеиваются в одно обращение; после длинной части бот ждёт продолжения не меньше `SPLIT_JOIN_SEC`. Если «Грань» только в последней части — предыдущие длинные части того же автора тоже берутся;
- **`/роль (…)`** — если закрывающей скобки нет, бот ждёт следующих частей до `ROLE_JOIN_SEC` (15 с), пока скобка не придёт; не пришла — роль берётся до конца сообщения, и бот говорит об этом. `/роль текст` без скобок длиннее 3000 символов тоже ждёт продолжения;
- **«Грань, запомни текст…»** — так же.

Другой автор, другая команда или сообщение позже срока цепочку обрывают; частей не больше `SPLIT_MAX_PARTS` (20).

## База знаний (RAG)

Книги кладутся в папку `RAG` рядом с ботом (можно с подпапками): **txt, doc, docx, pdf (с текстовым слоем), epub, fb2, fb2.zip**. Индекс (`rag_index.db`) обновляется сам перед каждым вопросом к базе: новые и изменённые файлы индексируются, удалённые убираются. Перезапускать бота после добавления книги не нужно.

| Команда | Что делает |
|---|---|
| «Грань, РАГ вопрос» или `/раг вопрос` | ответ **строго по книгам**, с источниками («Источники: [1] «Название», Глава 2»). Если в книгах ничего не нашлось или модель решила, что ответа там нет — служебное сообщение «⚙️ В базе знаний ничего не нашлось.», без выдумок |
| «Грань, РАГ+ вопрос» или `/раг+ вопрос` | то же, а после строки `---` — ещё и обычный ответ модели (её знания, не книги). Если в книгах пусто — «ничего не нашлось», `---` и ответ модели |
| `/раг` без вопроса | что есть в базе: сколько книг и фрагментов, список файлов, какие не прочитались и почему |

Без косой черты «РАГ» срабатывает в обращении к боту, если написано заглавными или стоит сразу после «Грань,» — чтобы случайное «раг» в разговоре не включало поиск. Ответ по базе знаний расходует дневной лимит и ждёт конца `/паузы`, как `/пересказ`.

**Как «строго по книгам» обеспечено.** Модель получает только найденные фрагменты, пронумерованные, и промпт: отвечать только по ним, ссылаться на номера, а если ответа во фрагментах нет — ответить `НЕТ_ОТВЕТА`. Если поиск ничего не нашёл, модель **не вызывается вовсе** — «ничего не нашлось» приходит сразу, токены не тратятся. Фрагмент считается найденным, если в нём есть не меньше половины (`RAG_MIN_COVERAGE`) значимых слов запроса: одно случайное совпавшее слово из трёх не даёт «ответа» по постороннему тексту.

**Стек (бесплатный, работает без интернета и без GPU):**

- **pymorphy3** — леммы русских слов: «учил», «учение», «учения» сводятся к начальной форме и находят друг друга. Без него — стеммер Snowball, без того — слова как есть;
- **BM25** по леммам, индекс в **SQLite** (входит в Python) — классический полнотекстовый поиск, хорошо работает на точных терминах, именах и цитатах;
- **по желанию — векторный поиск** `intfloat/multilingual-e5-small` (sentence-transformers, ~0,5 ГБ с torch): находит фрагменты по смыслу, даже без общих слов. Включается `RAG_EMBEDDINGS = True`, результаты объединяются с BM25 (Reciprocal Rank Fusion). По умолчанию выключен: тяжёлый, а для книг по философии и точных вопросов лемм обычно хватает;
- **чтение книг** — стандартная библиотека Python (txt в UTF-8/UTF-16/cp1251/koi8-r — кодировка определяется сама; docx, epub, fb2 — это XML), **pypdf** для pdf, **olefile** для doc (если не вышло — `antiword`/`catdoc`, если установлены). Главы («Глава 3…», заголовки docx/epub/fb2) запоминаются и показываются в источниках.

Почему не LangChain/LlamaIndex и не векторная БД: для папки книг одного бота они добавляют сотни мегабайт зависимостей и сервис, а выигрыша не дают; весь модуль — один файл. Проверить поиск без бота: `python rag.py RAG "чему учил Сократ"`.

pdf без текстового слоя (скан) не читается: в `/раг` он будет в списке «не прочитан: текста не найдено» — нужно распознать его (OCR) заранее.

### «Грань, запомни» → Рефлексия.txt

Это возможно и сделано. «Грань, запомни» с пересланными сообщениями (или в ответ на сообщение, или с текстом после «запомни») **перезаписывает** `RAG/Рефлексия.txt` этим текстом и сразу переиндексирует только его; бот отвечает, сколько символов и фрагментов записано. Прежняя версия сохраняется в `Рефлексия.txt.bak` (её индекс не видит). По умолчанию команда только для админов беседы (`REMEMBER_ADMIN_ONLY`), чтобы кто угодно не мог переписать базу знаний.

## Роль по умолчанию — Роль.txt

Если рядом с ботом есть `Роль.txt`, его текст — роль по умолчанию во всех беседах (без файла — встроенная `DEFAULT_ROLE`, как в bot5; в комплекте файл с тем же текстом). Файл перечитывается, если изменился, — перезапуск не нужен. `/роль (текст)` задаёт роль беседе, `/роль` без текста показывает текущую, **`/сбросить роль`** возвращает роль по умолчанию из файла.

## Ожидание 7–8 секунд, чтобы ответить сразу нескольким собеседникам

**Да, это есть с bot5 и в bot6 осталось.** Бот ждёт `BATCH_WAIT_SEC` = 8 с после последнего обращения; если за это время к нему обратился ещё кто-то, ожидание продлевается, и бот отвечает **одним сообщением на всех**, называя авторов по имени (один запрос к модели, один ответ в дневном лимите). Чтобы при непрерывном потоке бот не молчал, через `BATCH_MAX_WAIT_SEC` = 60 с после первого обращения он отвечает в любом случае. После длинной части разрезанного сообщения ожидание — не меньше `SPLIT_JOIN_SEC` (10 с). Проверено тестом `test_two_speakers_within_wait_get_one_answer` и смоук-тестом `main()`.

## Лимит токенов «сбрасывается быстрее, чем за час»

Сам срок отсчитывается верно: и в bot5, и в bot6 лимит возвращается к стандарту ровно через `TOKEN_LIMIT_RESET_MINUTES` (60) минут после команды, и время хранится в БД (переживает перезапуск). Ощущение «сбросился раньше» дают другие причины:

1. **bot5 неверно понимал число.** `/лимит токенов 30 000` (с пробелом) он читал как **30**, `/лимит токенов 30к` — тоже как 30, а `/лимит токенов: 3000` (с двоеточием) — как команду без числа (только показывал текущий лимит, ничего не меняя). Проверено на регулярном выражении bot5. При лимите 30 ответы обрывались или выходили пустыми — похоже на «лимит не действует».
2. **Рассуждение ест лимит.** Даже при большом лимите видимый ответ может быть коротким: модель сначала тратит токены на рассуждение (см. [выше](#почему-запросы-уходят-а-бот-пишет-не-получилось-сформулировать-ответ--мысль-не-родилась)).
3. **Роль просит кратко.** В системном промпте бота есть «Отвечай кратко», поэтому модель и с лимитом 30000 обычно отвечает в несколько абзацев. Лимит — потолок, а не требуемая длина: для длинного ответа его нужно попросить («подробно, в нескольких разделах») или поменять роль.

В bot6: `/лимит токенов` понимает «3000», «: 3000», «30 000», «30к», «30k»; в ответе на команду, в `/лимит токенов` без числа и в `/помощь` видно, **до скольких** действует лимит («30000 (до 15:40, потом 800)», «В 15:40 (через 60 мин) вернётся к стандарту 800.»); когда срок вышел, бот пишет в беседу «Прошло 60 мин с «/лимит токенов 30000» (задан в 14:40) — лимит токенов вернулся к стандарту 800.»; в логе — строка с лимитом каждого запроса.

## Новые настройки

Все — в начале `bot6.py`, в блоке `НАСТРОЙКИ`.

| Переменная | По умолчанию | Что значит |
|---|---|---|
| `EMPTY_ANSWER_RETRY_TOKENS` | 3000 | пустой ответ из-за лимита — один повтор с таким лимитом; 0 — без повтора |
| `LLM_EXTRA_BODY` | `None` | доп. параметры запроса к модели (например, выключить рассуждение) |
| `SPLIT_MIN_PART_CHARS` | 3000 | сообщение такой длины может продолжиться следующим |
| `SPLIT_JOIN_SEC` | 10 | продолжение приходит не позже стольких секунд |
| `SPLIT_MAX_PARTS` | 20 | больше частей не склеивать |

## Запуск

```bash
cd Прочее/bot6
pip install -r requirements.txt
python bot6.py                 # или python bot6_server.py на сервере
```

Файл `.env` — как у bot5 (`VK_TOKEN`, `VK_GROUP_ID`, `PROXYAPI_KEY`, `ADMIN_IDS`, `VK_USER_TOKEN`). Если рядом с bot6 его нет, бот берёт `.env` из текущей папки, затем из `../bot5`.

**Переход с bot5.** bot6 пишет в новую базу `gran6.db`. При первом запуске он переносит из `gran5.db` (рядом с ботом, в текущей папке или в `../bot5`; или путь из `OLD_DB_PATH`) историю, роли, имена, метки `/забудь`, настройки `/лимит символов` и начало истории бесед — загружать историю из ВК заново не нужно. Перенос делается один раз.

## Что не проверено

На живом сообществе и живой модели bot6 не запускался. В частности, не проверено на практике:

- что ProxyAPI отдаёт для `deepseek-v4-flash` `finish_reason` и `usage.completion_tokens_details.reasoning_tokens` (если нет — повтор и причина всё равно работают по пустому ответу, но без числа токенов рассуждения), и какой `LLM_EXTRA_BODY` выключает рассуждение;
- что после перехода на `certifi` картинки скачиваются на машине из задачи (сертификат HARICA в `certifi` есть — это проверено);
- как ВК режет длинные сообщения на практике (интервал между частями и их длина): склейка рассчитана на части от 3000 символов с промежутком до 10 с — при необходимости поправьте `SPLIT_MIN_PART_CHARS` и `SPLIT_JOIN_SEC`;
- качество ответов модели по базе знаний на больших книгах.
